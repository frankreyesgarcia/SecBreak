# Manual BC-Detector Validation — Labeling Guide

**Purpose.** Establish a measured precision/recall for the automated breaking-change
(BC) detector by hand-checking a stratified sample of its verdicts. The
pre-submission gate wants **at least 20–30 rows adjudicated** with a reported
precision and recall before the paper is submitted.

**Your job.** Open `results/manual_validation_sheet.csv`, and for each row fill in
two cells: `label` (one of `TP` / `FP` / `FN` / `TN` / `unsure`) and `notes` (free
text — a phrase is fine). Nothing else in the sheet should change. Labels are
**not** to be generated by a tool or model; the point of the gate is a human
signal.

**What the detector is.** For Maven rows (`detector = roseau`) the verdict comes
from Roseau, a source-level API compatibility checker. For PyPI rows
(`detector = griffe`) it comes from a lighter version-isolated public-signature
diff. Metrics are reported **overall and split by detector**, because the paper's
headline BC claim rests on the Maven/Roseau subset.

---

## How to read a row

| Column | Use |
|---|---|
| `sort_rank` | Labeling order. Rows 1–54 have a curated dependency changelog link; 55–90 have a changelog/release-notes excerpt from the PR body; 91–100 have neither. **Label from the top** — the early rows are the ones you can decide with most confidence, which is what the gate's first 20–30 should be. |
| `detector_verdict` | What you are checking: `BC` = detector claims ≥1 breaking change; `no-BC` = detector claims none. |
| `bc_count`, `bc_types` | For `BC` rows: how many API-level BCs Roseau/griffe reported and a rollup by kind (`METHOD_REMOVED x12; TYPE_REMOVED x3; …`). This is the claim to confirm or refute. |
| `pr_diff_snippet` | The dependency version bump (reconstructed) plus a link to the full file diff. Dependabot PRs only change the dependency version in the manifest, so the *code* impact lives in the dependency, not the PR. |
| `changelog_excerpt` | Release-notes / changelog text for the version range, pulled from the Dependabot PR body (truncated). Blank for ~21 rows. |
| `changelog_link` | Curated upstream changelog / releases / repo URLs (rows 1–54). |
| `pr_url` | The PR itself, if you want the Dependabot compatibility score or the full body. |

You do **not** need to re-run or re-derive detection. Judge from the diff, the
changelog, the reported `bc_types`, and — where you need it — a quick look at the
dependency's own release notes or source.

---

## The five labels

Assessed against **what the detector claims for that row**:

### `TP` — true positive
Detector said **BC**, and inspection confirms the update carries a **real
incompatible API change on the client-visible surface** (a removed / renamed /
retyped public method, field, constructor, or type; a new abstract method on a
public type; a narrowed return type; etc.). The changelog calling out "breaking
changes", a major-version bump with removed public API, or the `bc_types` clearly
matching real removals in the dependency's release notes are all sufficient
evidence.

### `FP` — false positive
Detector said **BC**, but the reported change is not a client-affecting breaking
change:
- the change is **additive** or otherwise backward-compatible;
- it touches only **internal / non-public / `@Deprecated`-and-hidden** API, or
  code a normal client cannot reference;
- it is a **detector artifact** — e.g. a version bump with no real API delta,
  shading/relocation noise, generics-only signal that does not break source or
  binary compatibility, or a comparison against the wrong artifact.

State the reason in `notes` (e.g. "internal package only", "all additions",
"generics-only, source-compatible").

### `FN` — false negative
Detector said **no-BC**, but the diff or changelog shows a **real breaking change
it missed**. Only assess this for rows where `detector_verdict = no-BC` — do
**not** go looking for breakage outside the 100 sampled rows.

### `TN` — true negative
Detector said **no-BC**, and that is correct: the update is a genuine
patch/compatible bump with no client-visible API removal or incompatible change.

### `unsure`
Genuinely ambiguous — e.g. a behavioral change with no clear surface signature, a
dependency whose changelog is uninformative and whose source you cannot quickly
assess, or a case that hinges on whether a borderline API is "public". Use it
rather than guessing. `unsure` rows are **reported separately** and are **excluded
from precision/recall**, not folded into TP/FP/FN/TN.

---

## Consistency

`label` must match the row's `detector_verdict`:

| `detector_verdict` | allowed labels |
|---|---|
| `BC` | `TP`, `FP`, `unsure` |
| `no-BC` | `FN`, `TN`, `unsure` |

`compute_manual_validation_metrics.py` flags any row that violates this (it will
list them under `inconsistent_rows` and leave them out of the counts) so a
mis-keyed label is caught rather than silently averaged in.

---

## When you have labeled ≥ 20 rows

```
python3 compute_manual_validation_metrics.py
```

It reads whatever is filled in (blank rows are skipped, no error), and writes
`results/manual_validation_metrics.json` with:

- `labeled_rows` / `total_rows` (e.g. `24 / 100`);
- `label_counts` including `unsure`;
- precision, recall, F1, accuracy with **95% Wilson confidence intervals** on
  precision and recall (the intervals matter at this sample size);
- the same block computed for `roseau` rows only and `griffe` rows only;
- `gate_met`: whether `labeled_rows >= 20`.

Re-run it whenever you label more rows.
